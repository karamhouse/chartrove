# Upstream reuse assessment — Chartrove production-first roadmap

**Decision status:** proposed for review, not an implementation order. **Evidence date:** 2026-11-05, Chartrove main `9ef8cad98bd7bde91e3a085161b7e1d4cea81cb4`. Source links point to independently maintained upstream repositories when available. Licenses, compatibility and data-flow implications require admission before use; public code does not imply permission to copy unlicensed data or bypass a provider's registration terms.

## Architecture boundary

Chartrove remains the application and database of record: Go/Gin backend, Angular 22 frontend, native Wails host and SQLCipher-encrypted local SQLite, with optional PostgreSQL for self-hosted use. Reuse **libraries, test fixtures and protocols**, not whole platforms that introduce a second patient store, credentials authority or deployment. Keep production-first correctness, restore/recovery, local data ownership, delegated authorization and genuinely usable FHIR/C-CDA ingestion ahead of speculative AI or Rust work.

## Controlled conversion comparison

1. Freeze current Chartrove import semantics, root/desktop modules, FHIR models, database encryption and test fixtures. Use disposable *synthetic* source data only.
2. Establish a common test pack of diverse C-CDA R2.1 examples: clinical sections, original IDs, payer information, references, nullFlavor, precision/offset dates, attachments and unsupported constructs. Record the original document, conversion warnings and provenance. Never synthesize missing clinical assertions.
3. Run Medplum `@medplum/ccda` first as a pure library prototype; run Microsoft converter against identical inputs. Metriport only if an unresolved fixture demonstrates a concrete advantage and its licensing is acceptable.
4. Measure preservation/error handling, correctly linked FHIR resources, duplicate/merge behavior, resourceType/marshaling consistency and round-trip limits. Compare actual Chartrove ingestion, SQLite encryption/reopen and packaging without external services.
5. Recommend the smallest adapter that passes; preserve lossless C-CDA originals and explicit partial-conversion warnings. No conversion library should silently treat a successful parse as clinical correctness.

## Deployment and migration decisions

- No Medplum CDR server, additional PostgreSQL/Redis healthcare stack, separate search index, or third-party hosted conversion in the baseline application.
- No immediate switch from the qualified Go FHIR fork to Samply; original-upstream preference is conditioned on validated compatibility.
- A Rust rewrite is **future-only**. Once daily-use acceptance is achieved, document stable FHIR, database migration, authorization, encryption/recovery, API and Wails/desktop contracts; run dual-implementation golden tests before any incremental change. No Rust rewrite branches or architecture migrations are authorized by this assessment.
- Do not work on the active Codex [#419 search-mode milestone](https://github.com/karamhouse/chartrove/issues/419) from this documentation PR. Live identity-provider acceptance stays separately gated by [#425](https://github.com/karamhouse/chartrove/issues/425).

## Proposed outcome

Accepted ADR(s) or follow-up issues may commission narrowly scoped synthetic tests for **C-CDA library selection** and **Inferno fixture improvements**, following the existing sole-writer protected PR workflow. This document neither installs dependencies nor approves a production data path.
